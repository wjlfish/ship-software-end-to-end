# 项目发现与基线核验

## 目录

- 一、读取指令与事实源
- 二、建立代码基线
- 三、建立运行基线
- 四、绘制改动面
- 五、形成根因或方案证据
- 六、处理脏工作树与并行工作
- 七、探查预算与停止条件

## 一、读取指令与事实源

先定位适用指令，不要从目录树盲扫：

```bash
pwd
rg --files -g 'AGENTS.md' -g 'CLAUDE.md' -g 'CONTRIBUTING*' -g 'README*' -g 'SECURITY*' -g 'CODEOWNERS'
```

先读取目录作用域内适用的仓库指令。若指令提供源码地图、目录或索引，只打开当前症状匹配的条目及少量直接相关的 ADR、runbook、事故记录和业务规则；只有指令明确要求时才通读全文或历史记忆。固定行号与旧 commit 只作线索；用当前文件和 `git log --grep=<标题关键词>` 重新定位。

同一事实冲突时：

1. 先尊重 system/developer/user 指令与明确授权；
2. 只读核对目标环境当前运行事实；
3. 核对当前仓库指令、代码、CI 和配置模板；
4. 把历史文档降级为线索；
5. 明确标注仍未验证的假设。

不要在输出中展示密码、token、私钥、证书正文或带凭据的远端 URL。

## 二、建立代码基线

普通任务只建立一次 Git 基线。优先运行仓库自带的基线脚本；项目陌生、工作树复杂或仓库没有相应入口时，再运行 Skill 的只读探针并手工补证：

```bash
python3 <本Skill目录>/scripts/project_delivery_probe.py --root .
git status --short --branch
git rev-parse HEAD
git rev-parse --abbrev-ref HEAD
git rev-parse --abbrev-ref --symbolic-full-name '@{u}'
git rev-list --left-right --count HEAD...'@{u}'
git log -10 --oneline --decorate
```

不要为了“核对”自动清理、stash、reset、checkout 或覆盖用户文件。需要刷新远端事实时，先确认 fetch 不会破坏当前协作约束；fetch 只更新远端引用，仍要处理本地脏改动和分叉。

记录：

- 正式工作区与仓库根；
- 当前 branch/commit/upstream；
- ahead/behind 与目标发布分支；
- 已修改、已暂存、未跟踪文件；
- 当前改动是否与任务重叠；
- 运行时版本文件、锁文件和包管理器；
- 单仓、多包、生成代码和构建产物边界。

从项目事实发现命令：

- `package.json` scripts、Makefile/Justfile、Taskfile；
- `pyproject.toml`、tox/nox、go.mod、Cargo.toml、pom/gradle 等；
- CI workflow 的实际版本、服务容器和命令；
- `scripts/`、`ops/`、`infra/`、`deploy/`、Docker/Helm/Terraform 等。

检查陌生脚本内容后再执行；不要因为脚本名叫 `test` 就假定它无副作用。

## 三、建立运行基线

若任务终点包含部署，必须在施工前和切流前各核对一次运行基线。使用项目已有的只读入口：

- 应用版本端点、release manifest、镜像 digest 或平台 deployment revision；
- 当前环境/region/account/project/namespace；
- 健康端点、实例数、队列/worker 版本；
- 数据库 schema/version 表；
- 配置键是否存在、来源和权限，不读取秘密正文；
- 近期错误率、告警和进行中的事故；
- 当前/上一安全版本和回滚方法。

如果平台 CLI 或 API 会变化，查阅该平台当前官方文档。不要用搜索结果摘要或过时博客代替项目 runbook 与官方资料。

把以下情况视为发布暂停条件：

- 线上版本与预期基线不一致且来源未知；
- 目标环境、账号、region 或 namespace 不明确；
- 正在发生事故或另一发布尚未结束；
- 回滚目标不可用；
- 所需配置、容量、证书、域名或权限未就绪；
- 数据迁移边界未确认。

## 四、绘制改动面

按“入口 → 规则 → 写入 → 消费者 → 运维”追踪，不只按文件名猜测。

### 入口

- UI、API、CLI、webhook、定时任务、队列消费者；
- 公开与鉴权入口；
- 新旧版本兼容入口；
- 移动端、桌面端、第三方回调等旁路。

### 规则与状态

- 领域规则、状态机、权限、角色、租户/组织/所有权；
- 校验和默认值；
- 幂等、重试、超时、租约、去重；
- 时间、时区、金额、精度和快照语义。

### 写入与读取者

- 表/文档/对象存储/缓存/搜索索引；
- 事务边界、唯一约束和外键；
- 报表、导出、后台、用户端、通知、审计；
- worker、cron、事件总线、数据仓库和外部系统。

### 交付面

- 构建入口、静态资源和动态 chunk；
- 配置模板、秘密挂载和运行时目录；
- migration、backfill、数据校验；
- health/smoke/monitor/rollback；
- 文档、ADR、操作手册和长期记忆。

用 `rg` 交叉验证所有同类入口。对“禁止、封闸门、权限、隔离、状态变更”类需求，搜索写入函数、路由、后台工具、CLI、worker 和旧兼容入口，明确证明没有旁路。

## 五、形成根因或方案证据

### Bug

把证据链压缩为：

1. 观察到的现象与复现条件；
2. 第一个偏离预期的不变量；
3. 导致偏离的代码/数据/配置；
4. 为什么现有保护未拦住；
5. 最小修复点与所有同步消费者。

区分根因和后果。例如“页面为空”可能只是 API 被错误权限过滤的结果；不要只在页面加兜底。

### 功能或新项目

把方案链压缩为：

1. 当前能力缺口；
2. 用户可观察验收条件；
3. 最小数据与接口变化；
4. 向后/向前兼容方式；
5. 测试、上线、回滚和观测方式。

如果没有既有发布设施，把“先建立最低可回滚交付路径”列入改动面，而不是发布当天临时拼命令。

## 六、处理脏工作树与并行工作

- 把现有变化视为用户资产；先确认它们属于谁、是否与任务重叠。
- 尽量编辑不重叠文件；重叠且无法安全合并时请求用户决定。
- 不运行 `git reset --hard`、`git checkout --`、宽泛清理或递归删除。
- 暂存时逐文件列出目标；提交前比较 `git diff` 与 `git diff --cached`。
- 只有在授权允许且并行确有收益时才使用代理；仅在开工阶段安排一轮互不重叠的只读调查、测试或明确独占文件，不递归扩散、不因失败补派。合并前由主负责人复核全部 diff 和证据。
- 若本地落后远端且工作树脏，不自动 pull/rebase；先保护现场，再选择新 worktree/分支、人工合并或暂停。

若仓库指定 canonical/primary checkout 只用于观察、集成或发布，所有修改必须从真实远端目标分支创建独立 worktree；不要在 primary checkout 直接施工。

## 七、探查预算与停止条件

开工时固定一张简洁检查清单：需求差异、预计改动文件、环境能力、直接相关测试、发布/生产步骤。优先服从仓库给定的探查次数、时间和代理预算；仓库未规定时，也为范围明确的普通任务设置小的初始探查预算（例如至多 5 次集中探查、约 5 分钟）。该预算只控制开放式发现，不是任务总预算；高风险或陌生项目按证据需要调整，完成任务所需的定向读取不受它阻断。

每次读取或搜索都应回答一个已知问题，并尽量合并相邻的只读检查。达到以下任一条件即停止扩大探查并进入实施或交付：

- 根因或能力缺口已有直接证据；
- 本问题入口、相关旁路、改动文件和直接回归已明确；
- 剩余未知不会改变方案，只影响可选优化；
- 已达到仓库预算或自定的初始预算；
- 缺失信息需要新的权限、用户选择或外部状态变化。

“找全旁路”不等于“再扫一遍全仓”。预算耗尽时应转入完成优先模式：禁止新的开放式审计，但允许且要求继续当前实现、围绕具体错误的定向读取、修复失败、必需验证、CI、部署和烟测。除真实外部阻塞或用户明确要求停止外，不得因达到预算而报告阻塞或结束任务。范围发生实质变化时更新检查清单；不要在收尾阶段重新开启无界审计。
