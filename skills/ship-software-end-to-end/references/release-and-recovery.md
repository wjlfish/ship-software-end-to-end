## 一、先选择现有发布适配器

优先沿用项目已经验证的方式，避免为了统一风格重写发布体系。

### 托管平台 / Serverless

- 用平台的 project/environment/preview/production 隔离和原生 revision。
- 固定 CLI/Action 版本，核对账号、region、project 与生产别名。
- 把 build artifact 与 runtime config 分离；部署后读回 revision 与流量指向。
- 验证冷启动、环境变量、绑定、定时任务、域名和边缘缓存。

### 容器 / Kubernetes

- 使用不可变镜像 digest，不只用可漂移 tag。
- 分离 build、scan、push、deploy；记录 source revision 与 SBOM/摘要（项目支持时）。
- 使用 rolling/canary/blue-green 与 readiness；核对旧新 Pod 并存时的协议兼容。
- 验证 Deployment/Job/CronJob、migration Job、配置和 secret revision。

### 虚拟机 / 裸机

- 优先使用 `releases/<id> + shared + current/previous` 或同等不可变目录模型。
- 上传到隔离 incoming，服务端二次校验后登记为只读版本；正式 release 不可覆盖。
- 用原子符号链接/rename 切换，重载服务后烟测；运行时上传、日志、秘密放 shared。
- 禁止直接编辑在线目录或用 destructive sync 清理 current。

### 静态站点 / CDN

- 先上传内容寻址或 hash 资源，再切换入口 HTML/manifest。
- 保留入口引用的所有动态 chunk、worker、WASM、字体和 vendor 文件。
- 对 CDN invalidation/缓存版本化有明确策略；公网验证 DNS、TLS、边缘缓存与深链。
- 回滚入口前确保旧 hash 资源仍保留。

### 桌面 / 移动 / 人工商店发布

- 把签名、构建、分发、审核和灰度视为不同阶段。
- 记录二进制摘要、版本号、构建号、签名身份和商店状态。
- 若无法即时回滚，强化分阶段开关、远程配置和兼容窗口。

如果项目部署平台或 CLI 当前行为不确定，读取项目 runbook，并只查对应平台的当前官方文档。

## 二、无流水线时确认实际安全缺口

没有 CI/CD 不自动等于不能发布。先确认本次目标能否通过已有平台或简洁受控流程做到：源码与制品可追溯、权限和秘密受控、目标明确、失败可恢复、上线可验证。

只补与本次安全交付直接相关且已授权的缺口。完整测试矩阵、独立 staging、制品仓库、可观测平台或灾备体系按实际风险和项目要求采用；不能把建设整套平台作为小任务前置。确实缺少必要安全能力时说明具体风险，完成安全准备后请求所需决策，不以临时覆盖在线文件绕过。

## 三、构建一次并晋升同一制品

推荐流水线：

```text
source commit
  → lint/test/integration
  → production build
  → package + manifest/digest
  → artifact registry
  → staging verification（适用时）
  → production deploy 同一摘要
  → activate
  → smoke + revision check
```

制品门槛：

- 工作区与目标 commit 可追溯；本地未 push commit 不得成为生产唯一来源。
- 使用锁文件和固定工具大版本；构建后工作树不被污染。
- manifest 覆盖常规文件、符号链接或镜像层；服务器/平台再次验证摘要。
- 禁止打包秘密、证书正文、上传、日志、缓存、测试数据库和本地依赖目录。
- 正式制品 ID 不可覆盖；重复部署相同摘要应安全、可识别。
- PR 只构建和验证，不获得生产 secret；第三方 CI 依赖固定版本或完整摘要。

部署前比较“生产 current revision..目标 revision”的累计差异，不只看最后一个 commit。迁移、配置、基础设施和 worker 变更都要纳入。

## 四、数据库与状态迁移

先分类兼容性：

| 类型 | 推荐顺序 | 代码回滚边界 |
|---|---|---|
| 无状态/无 schema | 部署 → smoke | 可直接回旧制品 |
| 向后兼容扩展 | expand migration → 新代码 → backfill → 后续 contract | 兼容窗口内可回旧代码 |
| 新代码先兼容 | 部署兼容代码 → migration → 开启功能 | 关闭开关并回旧代码 |
| 不兼容 schema | 登记制品 → 维护/停写 → 即时备份 → migration → 立即激活 | 通常需同时恢复数据或安全前滚 |
| 长时 backfill | 先加 schema → 可续跑/限速 backfill → 对账 → 切读写 → 后续清理 | 每阶段单独定义 |

执行要求：

- 生产前在同引擎/主版本的隔离库演练从零与升级路径。
- 生产只执行本次目标范围，避免误重放全部历史迁移。
- 迁移前做即时备份并验证可读；重要变更恢复到临时库抽查。
- 从目标制品读取迁移文件，不从仍指向旧代码的 current 路径猜文件。
- 迁移后验证 schema、索引、约束、计数、金额、不变量与 migration marker。
- 记录配置/基础设施是否在制品外单独变化；代码回滚不会自动回滚它们。
- 新版本已产生写入后，不机械恢复旧备份覆盖新数据；评估 PITR、补偿或前滚。

对对象存储、搜索索引、消息格式、缓存 schema 和第三方 webhook 同样建立版本兼容窗口。

## 五、激活、烟测与并发

切流前确认以下证据仍有效；已有发布脚本完成的核对无需人工重复：

- 当前生产 revision 没有意外漂移；
- 目标 artifact digest、配置、容量和证书就绪；
- migration gate、备份和恢复点已满足；
- 上一安全版本真实存在；
- 没有另一发布/事故占用环境。

激活使用平台原生或原子操作。把“登记制品”和“切流”分开，让前置失败不影响 current。

部署锁至少保护切流和版本记录。若 smoke 不在同一锁内：

- smoke 开始前和结束后都读取 current revision；
- 任一时刻不等于目标 revision 即判结果无效并停止；
- 不把另一版本的健康误记为本次成功。

自动回滚前确认目标版本确实已经激活。SSH、锁或目标校验在切流前失败时，不要无条件回到 `.previous`，否则可能把本来没变的 current 再退一版。

smoke 同时覆盖源站与用户真实路径（按项目需要）：

- health/readiness/version；
- 关键入口、授权和隔离负例；
- 静态/动态资源；
- 数据迁移不变量；
- worker、队列和定时任务；
- 本次启动后新增错误；
- 公网 DNS/TLS/CDN/WAF。

## 六、回滚、前滚与灾难恢复

### 代码回滚

- 切回上一不可变制品；重载/重启服务；重新 smoke；核对 current revision。
- 保留刚失败版本用于诊断，不在生产内直接修补。
- 支持再次前滚，避免回滚脚本破坏版本历史。

### 数据不兼容

- 若旧代码能读写新 schema，可先回代码再处理数据。
- 若旧代码不兼容，保持维护或只读并优先修复前滚。
- 必须恢复备份时，先保存当前“坏但最新”的数据，再按恢复点/PITR/补偿保留新写入。

### 基础设施与外部状态

- 代码 release 不会自动恢复 DNS、证书、secret、Nginx/Ingress、队列配置、feature flag 或第三方控制台。
- 为这些变更分别做备份、diff、验证和反向步骤。
- 删除/缩容/密钥轮换等不可逆动作单独请求授权。

### 灾难恢复

- 定期演练从备份恢复到隔离环境，而不只验证备份文件存在。
- 记录 RPO/RTO、备份保留、异地副本、PITR 窗口和恢复负责人。
- 每次恢复前先留存当前状态；恢复后运行数据核对和全量 smoke。

## 七、发布后的观察与维护

- 观察错误率、延迟、吞吐、资源、队列深度、worker 心跳和关键业务指标。
- 高风险变更按未覆盖风险观察调度/回调；低频真实业务保留明确的自然验收项，区分部署完成与业务验收。
- 把告警阈值、日志链接、release ID、变更时间和回滚点写入发布记录。
- 仅在当前与上一安全版本稳定后轮转旧制品；至少保留额外一个已知安全版本。
- 不用 `--delete` 或宽泛递归删除清理在线目录；逐个确认目标和可恢复性。
- 更新 runbook/ADR/项目记忆中的长期事实，清理已完成待办，保留真实未验收项。
