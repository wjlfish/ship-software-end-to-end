# 软件全周期交付

## 目标

把一次软件任务交付成可追溯的闭环，而不是只交付一份本地 diff。始终从项目事实中发现技术栈、验证命令和发布设施；复用本流程的质量门，不硬编码某种语言、云平台或分支模型。

## 先确定执行边界

按用户实际授权选择终点：

- 用户只要求回答、评审或诊断：只做只读调查并交付结论，不写代码、不提交、不发布。
- 用户要求改代码但未要求发布：完成到本地验证和清晰交接；不得擅自 push、建 PR 或部署，除非仓库规则已经明确授权这些动作。
- 用户要求“上线、发布、部署、交付到底”或仓库规则明确每次改动必须部署：走完整流程，直到目标环境版本、烟测和观测证据都成立。
- 需要新的不可逆权限、生产数据操作、真实付款/消息/邮件、停机窗口或用户业务选择时，先完成所有安全的准备工作，再请求明确授权。

不要把终点授权扩张成其他外部动作。部署授权不自动包含制造真实订单、真实扣款、向真人发送消息或删除生产数据。

## 坚持七条规则

1. **事实优先**：在不覆盖更高层指令的前提下，按“目标环境当前运行事实与配置（只读核对）→ 当前仓库指令 → 当前代码、测试和流水线 → 历史文档/记忆 → 假设”判断现状。应有行为仍由当前用户要求、已批准规则和验收标准决定；生产现状本身可能正是待修缺陷。
2. **先证据后改动**：Bug 要先说明“根因是 X，证据是 Y”；功能要先说明“缺口是 X，选择方案 Y，因为 Z”。未定位完整入口和旁路前不要动手。
3. **最小且可逆**：只改实现目标所需的面；预先定义失败关闭方式、数据恢复边界和回滚/前滚方案。
4. **项目命令优先**：从仓库脚本、CI 和锁文件发现版本与命令，不凭习惯猜 `npm test`、部署目标或数据库迁移方式。
5. **保护用户现场**：识别并保留脏工作树、未跟踪文件和并行工作；逐文件暂存，禁止为省事覆盖、清理或混入用户改动。
6. **完成必须可证明**：CI 仍在运行、部署未切换、迁移未执行、烟测未通过、线上版本未核对，均不能声称任务完成。
7. **有界快速收敛**：优先服从仓库规定的探查时长、工具次数和验证批次；仓库未规定时，也要为范围明确的普通任务设置小而明确的工作预算。合并同类只读检查，同一 diff 的同一验证只运行一次；证据已足够时实施或交付，不用“再全面看一遍”延长任务。

## 开工与资源路由

第一次进入项目、恢复中断任务或发布路径不清楚时：

1. 先读取适用的 `AGENTS.md`、`CLAUDE.md` 或同类仓库指令；除非指令明确要求全文读取，否则只按目录、源码地图或索引打开当前任务匹配的章节，以及少量直接相关的 ADR、runbook 或记忆。不要把通读历史资料当作开工前置。
2. 优先使用仓库自己的基线检查脚本。项目陌生、工作树复杂或交付路径不清楚时，才运行通用只读探针：

   ```bash
   python3 <本Skill目录>/scripts/project_delivery_probe.py --root <项目目录>
   ```

   把输出当作启发式索引，逐项回到原文件核实；探针不会访问生产、读取凭据或决定该执行什么命令。
3. 首次编辑前固定一张简洁检查清单：需求差异、预计改动文件、环境能力、直接相关测试、是否需要发布及生产步骤。范围变化时显式更新，不在收尾阶段重新开启全面审计。
4. 只有在授权允许且并行确有收益时，才在开工阶段安排一轮互不重叠的只读调查或测试；子任务共享主任务预算、不得递归扩散，始终只保留一个改动面负责人。
5. 首次接手、工作树复杂或发布设施未知时，读取 [project-discovery.md](references/project-discovery.md)。
6. 确定改动面后，读取 [verification-matrix.md](references/verification-matrix.md) 选择验证层级。
7. 需要部署、迁移、回滚或新建流水线时，读取 [release-and-recovery.md](references/release-and-recovery.md)。
8. 需要形成计划、发布记录、审计报告或交接时，使用 [evidence-templates.md](references/evidence-templates.md)。

## 五段式执行

每段至少给用户一句简短、可核查的进度更新。不要让用户在长时间工具执行中失去上下文。

### 1. 对齐

用 1–3 句复述：

- 要改变的用户/业务结果；
- 明确约束和不在范围内的事项；
- 可观测的完成标准，包括是否必须上线。

把模糊愿望转成验收条件。只有会实质改变方案或产生高风险外部影响的缺失信息才阻塞；其余做合理、可撤销的假设并明确记录。

遇到“继续、接续、收尾、中断恢复”时，先恢复原任务末尾、交接和当前 diff，整理不超过 5 条不可变验收标准及已完成/未完成项；恢复前不重新全面审计或修改代码。原上下文确实不可得时，明确缺失，只按现有交接推进。

### 2. 定位

按任务风险建立必要基线：

- **代码基线**：仓库根、当前分支/commit、upstream、ahead/behind、工作树状态和已有用户改动。
- **运行基线**：仅当任务涉及发布、生产排障、migration 或运行环境事实时，核对目标环境版本/镜像摘要、健康状态、部署拓扑、配置来源和数据版本；避免输出秘密。
- **改动面地图**：入口、写入点、读取者、异步消费者、权限/租户边界、缓存、资源构建、数据表/迁移、外部系统、文档和测试。
- **交付路径**：项目规定的 lint/test/build/package/CI/deploy/smoke/rollback/monitor 命令与负责人。

普通任务只做一次 Git 基线检查。Bug 按“症状 → 责任层 → 首查入口 → 本问题全部同类入口”定位；“找全”是找全该问题的旁路，不是全仓审计。闸门、权限、状态机、资金和租户隔离问题必须搜索全部相关旁路，不能只修可见 UI。

### 3. 根因与方案

在改第一行代码前交付以下结论：

- Bug：陈述单一主根因、直接证据、为何现有测试未拦住，以及哪些现象只是结果。
- 功能：陈述当前能力缺口、最小设计、接口/数据兼容性和拒绝的替代方案。
- 列出完整改动面与风险：授权隔离、数据损失、并发/幂等、资金或外部副作用、缓存/静态资源、版本兼容、可观测性。
- 预先写出验证矩阵和失败恢复方案；涉及数据时先确定备份、恢复演练和旧/新版本兼容窗口。

安全事故、越权、资金错账或数据丢失等高严重度结论在扩大改动或执行恢复前做独立复现/第二证据源核对，避免把静态代码气味直接升级成生产事实。

先对照已确认业务规则、历史事故和误报记录，避免把设计当 Bug 或把旧文档当现状。

若接手时已有 diff，对它做一次完整审阅，集中收集同批问题并统一修改。之后只有范围变化或验证暴露新证据时才回看对应部分，禁止“最后再看一次 → 再补一个”的无界循环。

### 4. 施工与验证

实施最小改动集并同步补回归保护：

- 先做一次环境 preflight：确认项目要求的运行时、受影响依赖和本机服务能力。缺少可安装依赖时只安装一次；本机明确没有必要运行时或数据库时，直接交给项目 CI/隔离环境验证，不反复尝试已知不可运行的命令。
- 沿用现有架构、语言和格式；不顺手重构高风险链路。
- 服务端保留最终权限、输入、租户/所有权和状态校验；前端校验只作体验层。
- 对并发、重试和外部回调使用事务、唯一约束、幂等键、租约或明确的失败关闭语义。
- 对数据库优先使用 expand → migrate/backfill → contract；迁移需可在新库与升级路径演练，并验证行数、约束、索引和重跑语义。
- 把秘密、运行时数据和上传与不可变构建产物分离；不把凭据写入 Git、日志、测试夹具或交接文档。
- 真实付款、退款、邮件、群消息等验证默认使用 mock、sandbox、预演或下一笔自然业务；未经授权不制造真实副作用。

默认先运行“根因直接回归 + 仓库已有的 changed-files 验证入口”，只 lint 改动代码、只构建受影响产物、只跑相关测试；多租户、鉴权、资金、支付回调、migration、共享核心和真实外部副作用再按风险升级。执行项目 CI 中的同版本、同命令；若不能运行某层，明确原因、替代证据和剩余风险。同一 diff 的同一检查只运行一次，相关文件变化或修复该检查失败后才重跑。

CI 失败时一次性读取该次运行的全部失败日志，在下一次提交前批量修完所有可本地复现项；不要用逐个 push 或盲目重跑代替归因。

提交前复核完整 diff、意图内文件、生成物、秘密和工作树；逐文件暂存，遵循项目的提交语言、作者和分支/PR 策略，不 force push。

### 5. 发布与交付闭环

优先使用仓库已经定义的 CI/CD 和制品晋升路径。没有流水线时，先建立 [release-and-recovery.md](references/release-and-recovery.md) 中的最低完备基线，再发布；不要临时把源文件直接覆盖到在线目录。

发布必须依次证明：

1. 目标 commit 已进入正确远端分支或评审流，CI 全绿；失败要诊断并修复，不能用盲目重跑掩盖。
2. 部署的是该 commit 生成的同一份不可变制品，具备版本、构建时间和摘要/清单。
3. 切换前重新核对生产基线、配置前置条件、迁移与备份状态、并发发布锁和回滚目标。
4. 数据变更按兼容性计划执行；DDL/外部迁移失败时不要假定自动回滚。
5. 通过原子、滚动、蓝绿或平台原生方式激活；发布失败立即停止扩散并按预案回滚或安全前滚。
6. 烟测覆盖健康、关键用户路径、鉴权/隔离、静态与动态资源、后台任务/队列、日志和错误率；避免产生不可撤销业务数据。
7. 再次读取目标环境当前版本/摘要，确认它与目标 commit/制品完全一致。
8. 按风险观察错误率、延迟、资源、队列和业务指标；记录观察窗口及未能做的自然业务验收。
9. 只有新增或改变长期业务口径、schema、部署拓扑、worker、外部服务或高频易错约束时，才更新运行手册、ADR、部署说明或项目记忆；普通 Bug、测试修复以及能从代码/Git 推导的事实不写流水账。不要把会漂移的行号、秘密或无验证的猜测固化为事实。

## 失败处理

- 本地/CI 失败：保留原始错误，定位首个根因，修复后重跑受影响层及必要回归层。
- 部署前置条件不满足：不切流，报告缺失条件和已经完成的安全准备。
- 激活或烟测失败：停止 rollout；确认数据库兼容后回滚同一制品链。若回滚会损坏新数据，保持维护状态并优先安全前滚。
- 生产版本漂移：停止发布，查明谁/什么改变了环境，重新确定基线；不得覆盖未知变更。
- 外部服务无法做真实验收：发布完成与业务验收分开报告，设置自然业务观察项，不伪造“已验证”。

## 最终交付格式

最终回复必须自洽，不依赖中途更新，并简洁回答：

- **改了什么**：用户结果与关键文件/组件；
- **验了什么**：实际运行的命令、测试层与结果；
- **线上状态**：环境、当前版本/制品摘要、烟测与观察结论；
- **回滚状态**：可回到哪里，数据兼容边界是什么；
- **遗留项**：明确未验证、需用户动作或需自然业务观察的事项。

若发布是完成标准，只有这些证据齐全才使用“已完成”。
